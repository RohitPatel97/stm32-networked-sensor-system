# Combined-project stress validation — October 17, 2026

Scope: the combined project on Windows with Python 3.12.14, the pinned gateway
dependencies, a real C firmware simulator built with undefined-behavior checks,
and localhost HTTP/WebSocket traffic. Both original project directories were
preserved. Reproduction commands and measurement gates are in
[STRESS-TESTING.md](../STRESS-TESTING.md).

## Fixes found by testing

1. **Subscriber queue completion:** removing an old event from a full queue did
   not complete its unfinished-task count. A drained queue could therefore hang
   on `join()`. Both discarded events and WebSocket sends now complete their
   queue accounting, including a send that raises a disconnect. The slow-consumer
   and disconnect regression tests verify draining and cleanup.
2. **Simulator pacing:** Windows event-loop timeouts could return before the
   requested delay elapsed, allowing frames to exceed their configured pacing
   ceiling. The source now checks a high-resolution deadline after each wakeup.
   A deterministic early-timeout regression verifies minimum frame spacing and
   child-process cleanup.
3. **Application lifecycle retention:** endpoint closures captured each app's
   hub/source while FastAPI's callable-classification caches held strong
   references to those functions. Repeated factory calls retained entire apps.
   Shared route handlers now obtain state through the current request or socket,
   and the shared lifespan obtains the current app's hub. No dependency cache
   internals are modified. Weak-reference tests cover both unused apps and apps
   that have served requests; another test verifies two apps keep separate state.

The first two regressions failed before the fixes in
[stress-regressions-before.txt](stress-regressions-before.txt). Both application
collection cases failed in [stress-lifecycle-before.txt](stress-lifecycle-before.txt).
The [incremental implementation/test patch](stress-fixes.patch) is relative to
the preceding October 17 sandbox source, which already contained the WebSocket
startup-race fix. The public REST OpenAPI document remains identical, as recorded
in [stress-api-contract.json](stress-api-contract.json).

## Sustained runtime

The final **600.03-second run passed all 25 checks**. It accepted all 50,880
fresh frames from 848 actual C-process boots, with 847 session changes and
1,472 injected stream reconnects. Both the fast subscriber and persistent
WebSocket delivered in order. The clients established 2,688 WebSocket connections
and processed 58,940 telemetry events in total, with zero connection failures or
ordering errors. All 54 HTTP readiness checks passed.

The intentionally malformed/obsolete traffic produced exactly 101 parse errors
and 1,213 sequence rejections. The deliberately stalled subscriber dropped
50,816 old events while retaining the latest 64; its queue drained successfully.
History stayed bounded at 120 readings. Sensor outages and recovery were observed
repeatedly. Shutdown reaped the child process and released every subscriber.

The achieved rate was 84.80 fresh frames/second against a requested pacing ceiling
of 200; scheduling, process startup, parsing, and instrumentation account for the
lower achieved rate. This is accelerated host simulation, not an STM32 acquisition
rate or UART bandwidth measurement.

Memory was sampled 54 times after a 60-second warmup. The following changes compare
medians of the first and last six post-warmup samples:

The earlier ten-minute run passed its single-service gates, but the additional

## Memory retention and shutdown

After ten warmup app creations, the original 200-cycle factory probe retained
21,398,950 Python bytes (20.41 MiB). The fixed 200-cycle test retained 48,987 bytes
(47.84 KiB), including measurement/framework overhead, and verified that all 200
discarded apps, hubs, and sources were collected. Private committed memory was
flat across the measured samples. Compare the
[before probe](stress-app-lifecycle-probe.json) with the
[final lifecycle report](lifecycle-stress-20261017.json).

Six complete localhost server start/stop cycles in the same process passed all
functional cleanup checks. After garbage collection, each left only the
controller task and one Python thread. Handles were 289 in the first five cycles
and 288 in the sixth. Working-set growth from cycle two to six was 344,064 bytes
(0.33 MiB); private-memory growth was 323,584 bytes (0.31 MiB).

The pre-fix [shutdown probe](stress-shutdown-cycles.json) stayed just below its
coarse 4 MiB memory gate, but its upward trend prompted the factory test that
reproduced the retention. A short startup pilot also exceeded a private-memory
slope gate; sustained measurements exclude the first 60 seconds rather than
treating startup allocation as evidence of a continuing leak.

## Serial failures and boot persistence

The production `SerialSource` passed 500 fresh C boot captures through 1,000
scripted serial ports. All ports closed exactly once; all 2,000 fresh frames
were delivered in order. The run recovered from 142 failed opens and 999 read
disconnects, accounting for all 1,141 retries. The 999 intentional sequence
rejections and 250 intentional oversized-record errors matched expectations;
there were no subscriber drops or device rejections. See
[reconnect-stress-20261017.json](reconnect-stress-20261017.json).

That serial run predates the application-factory refactor. Its source manifest
therefore has the earlier `app.py` hash; the runner does not import or use the
application module. All code it exercises is unchanged in the final version.

The firmware boot-journal test filled all 6,553 slots with 505 injected interrupted
writes across the five programming positions. Its 6,048 published boot IDs were
strictly increasing; exhaustion returned failure without programming another
word or publishing another ID. The strict-warning, undefined-behavior-instrumented
test passed. See [stress-boot-journal.txt](stress-boot-journal.txt).

## Final regression checks and limits

The final [host verification](stress-host-verification.json) passed **255 Python
tests and all four CTest suites**, Ruff, JSON Schema drift, and the shared
compiled-firmware fixture check. The Python suite includes six real
C-to-HTTP/WebSocket-to-production-dashboard-renderer scenarios. The only warning
was the existing upstream Starlette/httpx TestClient deprecation. Additional
script/test lint, JavaScript syntax, and Git whitespace checks passed.

All 116 original imported-source hashes still match and both original Git
working trees are clean. Stress services and simulator children shut down at
completion. No hardware was flashed, and no deployment or publication occurred.

Memory samples cover the gateway and bounded test clients in one process.
They do not measure browser heap, simulator process RSS, STM32 RAM, USB driver
behavior, physical flash power cuts, or Raspberry Pi endurance. Renderer checks
use the production JavaScript in a DOM harness, not a browser memory profiler.
The passing finite runs provide evidence for these workloads, not a proof that
every possible memory leak or hardware failure has been eliminated.
